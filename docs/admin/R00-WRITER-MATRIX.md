## 2. Phân Tích Các Nguy Cơ Xung Đột & Lệch Dữ Liệu Cốt Lõi

### 2.1. Nguy cơ Editor sản phẩm cũ ghi đè lên Product Studio
- **Hiện trạng:** Các endpoint legacy `PATCH /api/products/:id`, `PATCH /api/products/bulk-metadata`, `PATCH /api/products/metadata`, `PATCH /api/products/:id/versions/:vid`, `DELETE /api/products/:id` đều có câu lệnh kiểm tra:
  ```typescript
  if (await prisma.productStudio.findUnique({ where: { productId: id } })) 
    return NextResponse.json({ success: false, error: 'Use Product Studio to edit this product.' }, { status: 409 });
  ```
- **Lỗ hổng:**
  1. Nếu một sản phẩm **chưa từng được mở và lưu trong Product Studio**, nó hoàn toàn không có bản ghi trong bảng `ProductStudio`. Khi đó, toàn bộ các writer legacy trên **vẫn hoạt động bình thường** và tiếp tục ghi đè dữ liệu trực tiếp vào bảng `Product` theo chuẩn cũ!
  2. Endpoint tạo mới `POST /api/products` (gọi từ `/admin/products/new`) **không tạo bản ghi `ProductStudio`**. Do đó, mọi sản phẩm tạo từ trang `/admin/products/new` đều trở thành sản phẩm mồ côi không có Studio revision!

### 2.2. Nguy cơ Cron Publish Scheduler phá vỡ tính cô lập của bản nháp
- Trong file `src/app/api/cron/publish-scheduler/route.ts`:
  ```typescript
  const toPublish = await prisma.product.findMany({
    where: { publishAt: { not: null, lte: now }, status: "draft" },
    select: { id: true },
  });
  await prisma.product.updateMany({ where: { id: { in: ids } }, data: { status: "active" } });
  ```
- **Hậu quả:** Script này quét trực tiếp bảng `Product` và cưỡng bức đổi `status` thành `"active"`. Nó hoàn toàn bỏ qua bảng `ProductStudio`! Kết quả là:
  - Một sản phẩm đang được biên tập viên lưu nháp trong Studio (chưa hề nhấn xuất bản) có thể bị cron scheduler tự động bật `status='active'` trên Storefront nếu trước đó trường `publishAt` trong database cũ thỏa mãn điều kiện.
  - Snapshot xuất bản `ProductStudio.published` vẫn là `NULL`, dẫn tới việc trang PDP rơi vào nhánh fallback dữ liệu cũ hoặc hiển thị sai lệch!

### 2.3. Nguy cơ Đa nguồn chân lý (Multiple Sources of Truth)
1. **Giá & Biến thể:**
   - Nguồn 1: Bảng `Product` (`price`, `originalPrice`) và bảng `ProductVariant`.
   - Nguồn 2: Tài liệu `ProductStudio.draft` và `ProductStudio.published` (lưu trữ toàn bộ biến thể, cấu hình RAM/SSD, giá, bảo hành dưới dạng JSON document).
   - *Quy tắc chuẩn hóa:* `ProductStudio.published` là nguồn chân lý duy nhất cho nội dung hiển thị; bảng `Product` và `ProductVariant` chỉ là hình chiếu (projection) để phục vụ tương thích ngược cho các query SQL.
2. **Hình ảnh & Media:**
   - Nguồn 1: Bảng `ProductImage` (lưu trực tiếp `r2Key` và `url`).
   - Nguồn 2: Bảng `MediaAsset` và `MediaUsage` liên kết với từng revision của sản phẩm.
   - *Quy tắc chuẩn hóa:* Toàn bộ metadata media thuộc quyền sở hữu của `MediaAsset`. Bảng `ProductImage` chỉ là hình chiếu thứ cấp được sinh lại tự động mỗi khi sản phẩm được xuất bản.

## 3. Lộ Trình Cắt Bỏ & Khóa Toàn Bộ Writer Cũ

Để bảo đảm tính toàn vẹn 100% trước khi triển khai các gói tiếp theo, các writer cũ sẽ được xử lý theo lộ trình:

1. **Khóa ngay lập tức (R01–R03):**
   - Đóng `POST /api/products`: Trả HTTP 409 chỉ định chuyển sang `/api/admin/product-studio`.
   - Đóng `PATCH /api/products/:id`: Trả HTTP 409 cho mọi sản phẩm (bất kể đã có bản ghi Studio hay chưa).
   - Đóng `DELETE /api/products/:id`: Trả HTTP 409.
   - Vô hiệu hóa việc update trực tiếp `Product.status` trong `src/app/api/cron/publish-scheduler/route.ts`.
2. **Chuyển đổi UI (R02–R03):**
   - Thay thế nút "Thêm sản phẩm" tại `/admin/products` bằng liên kết dẫn trực tiếp tới Studio tạo Laptop hoặc Phụ kiện.
   - Ẩn toàn bộ form `/admin/products/new` và `/admin/products/[id]`, chuyển hướng URL tự động sang `/admin/product-studio?id=:id`.
3. **Thống nhất Bulk Action (R03):**
   - Viết lại API bulk metadata để thực hiện conditional write thông qua `writeStudio` service, bảo đảm sinh revision và đồng bộ cả tài liệu JSON lẫn projection SQL.
