## 3. Migration Mới: `0016_contact_management_and_order_cas.sql`

### 3.1. Nội dung Migration
Tạo file: `d1-migrations/0016_contact_management_and_order_cas.sql`
```sql
-- Migration 0016: Contact Management & Order Concurrency Closure
-- An toàn, có điều kiện IF NOT EXISTS, có thể re-run mà không lỗi.

-- 1. Bổ sung revision cho ContactSubmission (bắt đầu từ 1)
ALTER TABLE "ContactSubmission" ADD COLUMN "revision" INTEGER NOT NULL DEFAULT 1;

-- 2. Bổ sung startedProcessingAt cho ContactSubmission
ALTER TABLE "ContactSubmission" ADD COLUMN "startedProcessingAt" DATETIME;

-- 3. Tạo bảng ContactEvent (Append-only Timeline)
CREATE TABLE IF NOT EXISTS "ContactEvent" (
  "id" TEXT PRIMARY KEY,
  "contactId" TEXT NOT NULL,
  "action" TEXT NOT NULL,
  "fromStatus" TEXT,
  "toStatus" TEXT,
  "note" TEXT,
  "actor" TEXT NOT NULL,
  "createdAt" DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY ("contactId") REFERENCES "ContactSubmission"("id") ON DELETE CASCADE
);
CREATE INDEX IF NOT EXISTS "idx_contact_event_contact" ON "ContactEvent"("contactId");
CREATE INDEX IF NOT EXISTS "idx_contact_event_created" ON "ContactEvent"("createdAt");

-- 4. Backfill các ghi chú cũ thành sự kiện ban đầu
INSERT INTO "ContactEvent" ("id", "contactId", "action", "toStatus", "note", "actor", "createdAt")
SELECT
  'ce-backfill-' || c.id,
  c.id,
  'NOTE_ADDED',
  c.status,
  c.internalNote,
  COALESCE(c.handledBy, 'Admin vận hành (Phiên dùng chung)'),
  COALESCE(c.handledAt, c.updatedAt, c.createdAt)
FROM "ContactSubmission" c
WHERE c.internalNote IS NOT NULL AND c.internalNote != ''
  AND NOT EXISTS (
    SELECT 1 FROM "ContactEvent" e WHERE e.contactId = c.id
  );
```

### 3.2. Hướng Dẫn Rollback Tương Thích & Quản Trị Migration
- **Quy tắc Rollback ứng dụng an toàn (Backward-Compatible Application Rollback):**
  - Khi cần rollback phiên bản ứng dụng, chỉ rollback mã nguồn ứng dụng (code rollback) về commit ổn định trước đó.
  - **TUYỆT ĐỐI KHÔNG DROP TABLE `ContactEvent` hoặc xóa các cột lịch sử:** Bảng `ContactEvent` và các cột `revision`, `startedProcessingAt` có giá trị mặc định (`DEFAULT 1`, nullable) hoàn toàn tương thích ngược với mã nguồn cũ. Việc giữ nguyên bảng lịch sử bảo toàn toàn bộ dấu vết kiểm toán (audit trail) của hệ thống.
  - **Khôi phục dữ liệu (Data Restore):** Nếu phát sinh nhu cầu khôi phục trạng thái dữ liệu cũ, đây là một quy trình vận hành độc lập riêng biệt, chỉ được thực hiện từ bản sao lưu D1 backup chính thức (`wrangler d1 backup`) và phải có kế hoạch kiểm duyệt, phê duyệt văn bản phù hợp.
- **Quản trị triển khai Remote:**
  - Không mặc định R07 hay bất kỳ giai đoạn nào được tự ý migrate lên database remote/production.
  - Mọi thao tác migrate remote phải có gate nghiệm thu độc lập và lệnh kích hoạt tường minh được phê duyệt.

## 4. Cập Nhật Tài Liệu R06: Điều Chỉnh Các Tuyên Bố Cũ

Trong tài liệu `docs/admin/R06-ORDERS-CONTACTS-CUSTOMERS.md`, các tuyên bố sau đây đã được hiệu chỉnh chính xác theo R06.1:
1. **Giá trị revision ban đầu:** Đơn hàng (`Order`) có `revision` khởi tạo mặc định là `0` trong schema D1. `expectedRevision` bắt buộc là số nguyên không âm (`>= 0`). Liên hệ (`ContactSubmission`) có `revision` khởi tạo là `1`.
2. **Actor:** Xóa bỏ tuyên bố actor lấy từ client payload. Xác nhận toàn bộ audit trail và event sử dụng nhãn máy chủ `Admin vận hành (Phiên dùng chung)`.
3. **Danh tính khách hàng:** Không tự động gộp các đơn hàng vãng lai có cùng số điện thoại thành một tài khoản duy nhất. Mỗi đơn khách vãng lai là một bản ghi độc lập; các đơn khác cùng SĐT được gắn nhãn là "gợi ý chưa xác minh danh tính".
4. **Export CSV:** Sửa lỗi double-escaping; xác nhận đã chuyển sang kiến trúc chunking theo batch để tải đầy đủ không giới hạn 100/5000.
5. **Phân loại Browser QA:** Đổi tên từ "Real Browser Production UI QA" thành "Component Harness Browser QA (Scope D)" để phản ánh đúng bản chất kỹ thuật.
